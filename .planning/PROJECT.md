# CinderX LTO/PGO 性能修复项目

## 项目愿景

使 CinderX JIT 编译器能够安全、高效地使用 LTO（链接时优化）和 PGO（性能引导优化），在生产环境中获得最佳的运行时性能。

### 现状问题

当前 CinderX 在开启 LTO/PGO 后会出现严重的性能劣化甚至构建失败：
- **构建失败**: ARM 平台缺少 `LLVMgold.so`，无法链接
- **性能劣化**: LTO 破坏了 JIT 运行时函数的地址稳定性
- **PGO 不匹配**: 训练数据基于 CPython 测试套件，而非 JIT 工作负载
- **工具链限制**: macOS 不支持 LTO，限制开发环境

## 项目背景

### 什么是 LTO/PGO？

**LTO (Link-Time Optimization)**
- 在链接阶段进行跨模块优化
- 可内联函数、消除死代码、优化内存布局
- 通常可提升 5%~20% 性能

**PGO (Profile-Guided Optimization)**
- 基于运行时 profile 数据进行优化
- 优化分支预测、函数布局、缓存使用
- 通常可额外提升 5%~15% 性能

### 为什么 JIT 编译器难以使用 LTO/PGO？

传统 JIT 编译器（如 JVM、V8）与静态 LTO/PGO 存在架构冲突：

| 特性 | 静态编译（LTO/PGO友好） | JIT编译（动态） |
|------|----------------------|----------------|
| 编译时机 | 构建时 | 运行时 |
| 代码地址 | 链接时确定 | 运行时动态分配 |
| 函数边界 | 固定 | 动态生成 |
| 优化策略 | 全局分析 | 局部热路径 |

**CinderX 的特殊挑战**:
- 混合模式：既有静态编译的 JIT 运行时，又有动态生成的机器码
- 紧密耦合：JIT 生成的代码直接调用静态运行时辅助函数
- 地址敏感：`JITRT_*` 函数的地址被硬编码到生成的机器码中

## 成功标准

### 功能标准

- [ ] LTO 构建在 ARM64/X86_64 Linux 上零失败
- [ ] PGO 训练使用 JIT 密集型工作负载
- [ ] JIT 运行时函数地址稳定性保证
- [ ] 运行时性能劣化不超过 1%（vs 无 LTO）

### 性能标准

| 指标 | 当前状态 | 目标 | 验收测试 |
|------|---------|------|---------|
| Richards 基准 | 劣化 -10%~20% | 提升 +5%~10% | `pyperformance richards` |

| 编译时间 | 增加 50% | 增加 <30% | 构建计时 |
| 内存占用 | 增加 20% | 增加 <10% | RSS 监控 |

### 兼容性标准

- [ ] GCC 13+ 完全支持 LTO/PGO
- [ ] Clang 18+ 完全支持 LTO/PGO
- [ ] macOS 优雅降级（禁用 LTO，文档说明）
- [ ] CI/CD 流程包含 LTO/PGO 构建测试

## 技术约束

### 硬性约束

1. **不改变 JIT 核心架构**: 保持 HIR/LIR/IR 分层设计
2. **向后兼容**: 无 LTO 构建方式继续支持
3. **平台限制**: macOS 不支持 LTO（底层限制）
4. **性能底线**: 修复后性能不劣于无 LTO 版本

### 软性约束

1. **构建时间**: LTO 构建时间增加控制在 30% 以内
2. **内存使用**: 链接阶段内存占用不超过 8GB
3. **工具链依赖**: 尽量减少额外工具链依赖

## 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| LTO 引入难以调试的崩溃 | 中 | 高 | 分阶段启用、充分测试、保留无LTO回退 |
| PGO 训练数据收集失败 | 低 | 中 | 使用已知稳定的基准测试、多重试机制 |
| 性能提升不达预期 | 中 | 中 | 设定合理的期望（5%~10%）、持续调优 |
| 工具链兼容性问题 | 高 | 中 | 文档化已知问题、提供降级方案 |
